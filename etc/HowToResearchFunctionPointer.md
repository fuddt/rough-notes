# 関数ポインタ以降で詰まったときの追跡ガイド

## 目的

構造体が最終的に関数ポインタ経由で DLL に渡されるコードに遭遇したとき、

- どの関数が実際に呼ばれているのか
- どの構造体が DLL に渡っているのか
- その構造体の各メンバーが、元のどの値由来なのか
- DLL 内で使われているか、少なくとも DLL 入口まで到達しているか

を Visual Studio 2019 で調べるための手順をまとめる。

---

## 1. まず理解すること

関数ポインタ経由の呼び出しでは、見た目が普通の関数呼び出しに近くても、実際には

- 関数そのものを呼んでいるのではなく
- **関数アドレスを保持している変数** を経由して
- その先の関数を実行している

という構造になっていることがある。

例えば次のような形。

```cpp
using FuncType = int (__stdcall *)(const RequestParam* p);

struct FunctionTable
{
    FuncType target;
};

int ret = table.target(&param);
```

このとき `target` は関数そのものではなく、**関数ポインタ変数** である。
そのため `F12` で飛んでも、関数本体ではなく

- 型定義
- 構造体メンバー宣言
- 宣言のみのヘッダ

に行って止まることがある。

---

## 2. 典型的な詰まりポイント

関数ポインタ経由のコードで詰まりやすいのは主に次の3点。

### 2-1. 関数本体に飛べない

`F12` で進んでも、関数ポインタ型やメンバー宣言に飛ぶだけで、実装本体に到達しない。

### 2-2. 最初の構造体名が消える

元の構造体から DLL に渡るまでに複数回の詰め替えがあり、
途中で別構造体・別メンバー名に変わっていく。

### 2-3. DLL 内部が見えない

関数本体が DLL 側にあり、ソースが手元にない場合、通常の静的追跡では中身が見えない。

---

## 3. 方針転換が必要なタイミング

次のような状態になったら、追跡方法を切り替える。

- 元の構造体名を追っても途中で見失う
- 関数ポインタのメンバー宣言で止まる
- 関数本体が見つからない
- DLL 側に入っている気配はあるが、静的には追えない

この場合は、**最初の構造体から前向きに追う** のをやめて、
**DLL に渡す直前の最終構造体から逆流して追う**。

---

## 4. 調査の中心を「最終引数」に移す

関数ポインタ呼び出しが例えば次のような形なら、

```cpp
ret = dispatchTable.callTarget(&request);
```

ここで最重要なのは `request`。

この段階では、元の構造体名ではなく次を優先して調べる。

- `request` の型は何か
- その型のメンバーは何か
- 各メンバーにどこで値が入るか
- その値の元は何か

つまり、以後の起点は**「DLL に渡している最終変数」** にする。

---

## 5. 実務手順

## ステップ1: 関数ポインタ呼び出し行を特定する

まず、実際に関数ポインタを呼んでいる行を見つける。

例:

```cpp
ret = dispatchTable.callTarget(&request);
```

ここで確認すること:

- 何を引数に渡しているか
- `&request` なのか `request` なのか
- 呼び出し先が本当に関数ポインタメンバーなのか

---

## ステップ2: 最終引数変数の型を調べる

呼び出し行の引数変数の宣言へ飛ぶ。

例:

```cpp
RequestPacket request{};
```

ここで重要なのは、
**DLL に渡る最終構造体は `RequestPacket` 型である** と確定すること。

以後は、元の構造体よりもこの `RequestPacket` を中心に見る。

---

## ステップ3: 最終構造体のメンバー一覧を出す

`RequestPacket` の定義を開き、メンバー一覧をメモする。

例:

```cpp
struct RequestPacket
{
    int mode;
    int code;
    double value;
    int flag;
};
```

まずはこの段階で、
「DLL に渡る箱の中身」を把握する。

---

## ステップ4: 各メンバーの代入元を検索する

最終構造体の各メンバーについて、どこで値が入っているかを調べる。

検索例:

```text
request.mode =
request.code =
request.value =
request.flag =
```

見つけたいコード例:

```cpp
request.mode = middle.type;
request.code = source.status;
request.value = calc.value;
```

ここでやることは、
**最終構造体のメンバーごとに1本ずつ逆流線を作ること**。

---

## ステップ5: 1段ずつ逆流する

例えば

```cpp
request.code = middle.type;
```

が見つかったら、次に

```text
middle.type =
```

を検索する。

その結果、

```cpp
middle.type = source.mode;
```

が見つかれば、逆流線はこうなる。

```text
request.code <- middle.type <- source.mode
```

この形で、必要なメンバーだけ逆算していく。

---

## ステップ6: 元の構造体名に固執しない

途中で名前が変わるのは普通。

例えば次のようなことはよくある。

```text
source.mode -> middle.type -> request.code
source.value -> temp.amount -> request.value
```

このとき、名前一致で追おうとすると破綻する。
必要なのは、**代入文のつながり** を追うこと。

---

## 6. 関数ポインタ本体の見つけ方

関数ポインタの呼び出し先本体を知りたい場合は、
「呼び出し箇所」ではなく **関数ポインタへの代入箇所** を探す。

### 探すもの

```text
memberName =
GetProcAddress
typedef
using
```

典型例:

```cpp
functionTable.callTarget = RealFunction;
```

または

```cpp
functionTable.callTarget = (FuncType)GetProcAddress(moduleHandle, "RealFunction");
```

ここで初めて、
**関数ポインタが最終的にどの関数を指しているか** が見える。

---

## 7. DLL に入る前に確認すべきこと

DLL の中身が見えなくても、呼び出し直前で次は確認できる。

- 最終構造体の型
- 最終構造体の中身
- 各メンバー値
- 関数ポインタが null でないこと

つまり、DLL の入力までは確定できる。

この時点で最低限、
**「どの構造体を、どの値で、どの関数ポインタに渡しているか」**
を押さえる。

---

## 8. Visual Studio 2019 でのデバッグ手順

## ステップ1: 関数ポインタ呼び出し行にブレークポイント

例:

```cpp
ret = dispatchTable.callTarget(&request);
```

ここにブレークポイントを置く。

---

## ステップ2: 停止時に確認するもの

ウォッチまたはローカルで次を見る。

```text
request
&request
dispatchTable.callTarget
```

必要なら `request.member` も見る。

目的:

- DLL に渡る直前の構造体値確認
- 関数ポインタが有効なアドレスを持っているか確認

---

## ステップ3: F11 でステップイン

- ソースがあればそのまま入れる
- ソースがなくても逆アセンブリへ入れることがある
- 入れない場合でも、呼び出し直前の情報は取れる

---

## ステップ4: モジュールウィンドウを見る

Visual Studio で次を開く。

- [デバッグ]
- [ウィンドウ]
- [モジュール]

ここで見ること:

- どの DLL がロードされているか
- 対象 DLL のパス
- シンボルが読めているか

これで、
**実際にどの DLL に飛んでいるか** を確認できる。

---

## ステップ5: コールスタックを見る

ステップイン後に迷子になったら、次を開く。

- [デバッグ]
- [ウィンドウ]
- [コール スタック]

DLL 名や関数名が見えることがある。

---

## 9. DLL の中身が見える場合 / 見えない場合

### 9-1. DLL のソースがある場合

普通に `F12` や `F11` で追う。
DLL 側で最終構造体メンバーが参照されているか確認できる。

### 9-2. DLL のソースはないが PDB がある場合

関数名やコールスタックが比較的見やすい。
モジュールウィンドウとシンボル読み込みを確認する。

### 9-3. DLL のソースも PDB もない場合

この場合、C++ ソースとしては見えない。
ただし次は確認できる。

- どの DLL がロードされているか
- どの関数名を呼ぼうとしているか
- どの構造体をどの値で渡しているか

このとき DLL 内使用有無は、
**未確認ではなく「不明」** として扱うのが現実的。

---

## 10. 調査結果のまとめ方

最後は表にする。

| 最終構造体 | メンバー | 直接の代入元 | さらに前の代入元 | 元の由来 | DLL 到達 | DLL 内使用 |
|---|---|---|---|---|---|---|
| RequestPacket | mode  | middle.type | source.mode  | source.mode  | Yes | 不明 |
| RequestPacket | code  | source.code | -            | source.code  | Yes | 不明 |
| RequestPacket | value | calc.value  | source.value | source.value | Yes | 不明 |
| RequestPacket | flag  | localFlag   | -            | 不明         | Yes | 不明 |

こうしておくと、

- 何が DLL に届いているか
- 何が元の構造体由来か
- どこまで確定で、どこから不明か

が分かる。

---

## 11. 実務上の割り切り

関数ポインタ + DLL + 複数の詰め替えがあるコードでは、
最初から完全解明を狙うと破綻しやすい。

優先すべきは次。

1. DLL に渡る最終構造体を確定する
2. そのメンバーごとの代入元を追う
3. 元の構造体由来かどうかを切り分ける
4. DLL 内部が見えない場合は「不明」として止める

つまり、
**「分かるところまでを確定させる」** のが重要。

---

## 12. 最短版チェックリスト

- [ ] 関数ポインタ呼び出し行を見つけた
- [ ] DLL に渡している最終変数を特定した
- [ ] 最終変数の型を特定した
- [ ] 最終構造体のメンバー一覧を出した
- [ ] 各メンバーの代入元を検索した
- [ ] 少なくとも1メンバー分の逆流線を作った
- [ ] 関数ポインタへの代入箇所を探した
- [ ] DLL 呼び出し直前でデバッグした
- [ ] モジュールウィンドウで DLL を確認した
- [ ] DLL 内使用が見えなければ「不明」と分類した

---

## 13. 一言でまとめる

関数ポインタ以降で詰まったときは、

**最初の構造体から前向きに追わず、DLL に渡している最終構造体から逆流して追う。**

これが一番破綻しにくい。
